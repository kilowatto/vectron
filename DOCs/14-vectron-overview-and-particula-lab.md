## English

### §1. What we are trying to achieve with Vectron

Vectron is a **public, free, open-source 3D visualizer** that makes visible something that is normally completely invisible: how a large language model actually turns a word, a phrase, or a document into *numbers*, and how those numbers can be compared, searched, and retrieved. The bet behind the whole project is that most people who use ChatGPT/Claude/Gemini every day have zero intuition for what an "embedding" is, what "cosine similarity" means, or what actually happens when a chatbot does RAG (retrieval-augmented generation) over a document you upload. Vectron's job is to make that mechanism *seeable* — a real 3D space you can fly around in, where words that mean similar things really do end up physically near each other, because they are placed using **real embeddings** (not a toy/illustrative layout).

Concretely: every concept in the dataset is sent through a real embedding model, producing a genuine high-dimensional vector (768 dimensions today). That vector is mathematically compressed down to 3 coordinates (currently via a hand-rolled PCA — Principal Component Analysis — projection; UMAP is a possible later upgrade) so it can be placed as a glowing particle in a Three.js scene. Distance and clustering in that 3D cube are not decorative, but they are **not faithful either**: they are the optimal LINEAR 3D summary of a 1024-dimensional space. It preserves large-scale structure well and local neighbourhoods imperfectly. The measured figures, over the real seed embeddings (`worker/scripts/out/diagnostics.json`): **PC1–3 retain 10.89 %** of the variance, and neighbourhood preservation gives **trustworthiness 0.766 / continuity 0.837 at k=10** — i.e. roughly 23 % of what looks close on screen is NOT close in the full 1024 dimensions. Stored coordinates also go through three transformations (per-axis percentile rescaling, clipping to the cube edge and a local separation relaxation), so on-screen distance is not proportional to PCA distance in dense regions either. **The neighbour lists you see when you pin a particle are computed in the full 1024 dimensions, not from what is on screen.** When you type a word and its neighbors light up, that is a real nearest-neighbor query against a real vector index (Cloudflare Vectorize), not a lookup table.

The long-term ambition, honestly stated in the master plan, is large: a public dataset of **15,000 bilingual concepts** (currently paused around ~2,263 while other NOW-priority features land), a full RAG pipeline (upload a document → it gets chunked → chunks get embedded → a question retrieves the most relevant chunks → an LLM generates an answer grounded in them, all visualized), and eventually a live view into the Transformer's attention mechanism itself. That is a multi-month build for a single maintainer, so the project is deliberately sequenced as **DONE → NOW → LATER** rather than attempted all at once — see `02-master-plan.md` §11 for the exact phase table (P0…P10).

The whole thing is released under the MIT license, hosted at `vectron.kilowatto.com`, with the explicit goal of costing effectively **$0** to run at rest: the default dataset is precomputed once at seed time (not re-embedded per visitor), the default RAG path runs entirely client-side via WebLLM (a local in-browser LLM, no server inference cost), and any Claude-powered "premium" RAG mode is optional, off by default, and hard-quota-limited per user.

### §2. The educational content — three separate apps, not one app with a settings toggle

This is one of the most important, deliberately-locked product decisions in the whole project, so it's worth explaining *why* it's structured this way rather than just *what* it is.

**The core insight:** a curious teenager, a university student learning NLP, and a PhD-level ML practitioner do not just want "more detail" on the same screen — they want a genuinely different experience: different vocabulary, different density of information, different things treated as "given" vs. "explained," even a different visual layout. So instead of one app with a slider that reveals/hides jargon, Vectron ships **three distinct apps** that share the same underlying engine and dataset but present themselves completely differently. This is a locked rule (`MUST`): the names are always **Principiante / Intermedio / Avanzado** (Spanish) — never translated to "Beginner app" / "University app" / "Research app" in the UI, those are just internal audience labels used by the people building it.

**Principiante ("Wonder map")** — audience: teenagers, curious kids, older adults who've been impressed by ChatGPT and want to understand *anything* about how it works. Success looks like the visitor being able to say, in their own words, "it looks for nearby *ideas*, not the same letters" within about 90 seconds of arriving. All jargon is forbidden by default — no "cosine," no "ℝⁿ," no "BPE," no "PCA." Particles read simply as a sky of related ideas that light up together.

**Intermedio ("Mechanism lab")** — audience: university students, aimed specifically at an undergraduate AI curriculum ("Licenciatura en IA"). This is not a single screen but one laboratory with **three peer surfaces**: `Cube` (the token → embedding → cosine-neighbor mechanism, the same core visualization as Principiante but now correctly named and explained), `Transformer` (Input → **Context** → Attention → Blocks → Prediction, shown as a loop you can step through), and `RAG` (an external document archive → chunking → retrieval → feeding the Context → the Transformer). A specific, carefully-scoped **3D "Context Chamber"** exists as a chapter inside the Transformer surface — it visualizes the model's *working memory for this one conversation*, and it is explicitly never presented as the same data space as the meaning-cube, so students don't confuse "the space of all concepts" with "what the model currently remembers." Correct undergraduate-level vocabulary is used, with one-time tooltips rather than either dumbing it down or assuming prior knowledge. What Intermedio explicitly does **not** show: PhD-level attention heatmaps or the literal softmax/√dₖ attention equation in KaTeX — that belongs to Avanzado's Math Arena only.

**Avanzado ("Instrument")** — audience: PhD students and working data scientists / ML engineers who want the real thing, including where the visualization is an approximation and where it is not. Jargon is *required* here, not optional, but every approximation is explicitly declared rather than hidden. This surface exposes: two live tokenizers running side by side for comparison (the BGE WordPiece tokenizer vs. GPT's cl100k), live on-demand embedding calls against Cloudflare Workers AI (rate-limited per IP so cost stays bounded), a persisted PCA basis so the 3D projection is reproducible and stable across sessions (not re-randomized on load), per-vector Vectorize lookups, and hover-to-see the actual cosine similarity number on any connecting line. The planned "Math Arena" (permanent, not a collapsible "hide the math" panel) will add live Attention/Softmax/Cosine/PCA/Sampling instruments — toy-scale tensors are acceptable there as long as they're clearly labeled as illustrative, but cosine and PCA views must use the real dataset vectors first.

**A secondary, locked pedagogical layer** sits underneath the three apps: which *parts of speech* are visible acts as a difficulty ladder. Principiante shows only nouns and function words (articles, prepositions, conjunctions, auxiliaries). Intermedio adds adjectives. Avanzado adds verbs. This was deliberately *not* used as the primary curriculum axis (that would be a shallow "show/hide grammar" gimmick) — it is locked as a secondary visibility rule only.

**Current dataset:** roughly 2,263 hand-curated bilingual (Spanish/English) concepts across ~20+ semantic domains, each with a real embedding stored in Vectorize, a taxonomy, descriptive traits, a part-of-speech tag, and a 3D coordinate. The target is 15,000 concepts; growth is currently paused (not because of lack of ambition, but because the team decided to land the NOW-priority product features — phrase composer, mode-morph animation, HUD legends, the boot loader, RAG lite — before spending more curation budget on raw dataset size). Concept growth itself is largely automated now via a Cloudflare Cron job rather than being manually generated/reviewed batch-by-batch.

Every visual channel in the scene is meaningful, not decorative: XYZ position comes from the real PCA projection of the embedding; hue encodes the concept's root semantic domain (~20+ categorical colors); saturation/lightness encodes a subcategory or a continuous attribute within that domain; a halo/pulse effect shows dynamic relevance to whatever the visitor just typed. Every card also exposes its attributes as plain text, so the encoding is never color-only (accessibility requirement).

### §3. Technologies used

| Layer | Technology | Why |
|---|---|---|
| 3D rendering | **Three.js**, `WebGPURenderer` with automatic **WebGL fallback** | WebGPU gives access to Three.js's node-material system (TSL) and better performance at scale; WebGL fallback keeps the app usable on browsers/GPUs without WebGPU support yet |
| Frontend | **Vanilla TypeScript + native Custom Elements (Web Components, Shadow DOM)** — no React, Vue, or any app framework | Deliberate choice to keep the bundle lean and avoid framework churn for what is fundamentally a canvas-driven 3D app with a thin UI chrome around it; components are prefixed `vx-*` |
| Build tooling | **Vite**, `pnpm` workspace | Fast dev server + build; `pnpm` is the required package manager project-wide (never npm/yarn) |
| Hosting / backend | **Cloudflare, end-to-end** — Workers (API), Vectorize (vector index, 768-dim cosine similarity), D1 (SQL — taxonomy + per-IP quota counters), R2 (object storage for the precomputed dataset files), Workers AI (embedding inference) | Keeps steady-state cost near $0 (generous free tiers, no servers to keep warm) and keeps the whole stack on one platform |
| Embedding model | `@cf/baai/bge-base-en-v1.5` today, **migrating to `bge-m3`** | `bge-m3` has real multilingual support; the current pipeline only embeds the English word form, which under-serves the Spanish half of the audience — this migration requires a full breaking re-seed of the dataset |
| Dimensionality reduction | Hand-rolled **PCA** (3 components) computed once at seed time and persisted (`pca_basis.json`) so live token embeddings can be projected into the *same* stable 3D space session to session; **UMAP** is a possible later upgrade | Reproducibility matters more than using the fanciest projection — a basis that silently drifts between reseeds would make the "nearby = related" promise unreliable |
| RAG generation (default) | **WebLLM** — a small LLM run entirely client-side, in the visitor's own browser | Keeps the default RAG demo at $0 marginal cost, no server inference bill per visitor |
| RAG generation (premium, optional) | **Claude** (Anthropic) | Off by default; opt-in; hard daily quota per user so it can never become an open-ended cost |
| Internationalization | Custom `i18n.ts` with `es` (default) + `en` bilingual dictionaries, cookie-persisted language choice (`vectron_lang`) | The whole product — UI, concept labels, and every doc under `DOCs/` — is bilingual by explicit project rule, never English-only or Spanish-only |
| License / distribution | **MIT**, public repo `github.com/kilowatto/vectron`, live at `vectron.kilowatto.com`, API fallback at `vectron-api.esteban-rey.workers.dev` | Fully open source, including the pedagogical documentation itself |

Architecture, at a glance:

```
Browser (Vite + TS + Three.js webgpu/webgl)
  ├─ Principiante | Intermedio | Avanzado shells
  ├─ Particle engine + electric similarity lines + live token mode
  └─ (LATER) WebLLM local RAG
         │
Cloudflare Worker (vectron-api)
  ├─ /api/concepts · /api/similar · /api/cosine
  ├─ /api/embed (quota-limited) · /api/pca-basis · /api/similar-by-vector
  ├─ D1 (taxonomy + quotas) · R2 (dataset files) · Vectorize (768-dim cosine index)
  └─ Workers AI @cf/baai/bge-base-en-v1.5 (migrating → bge-m3)
```

### §4. The `/particula` lab — what it is, and what we're trying to prove there

**`/particula` is not part of the product.** It is not one of the three public apps (Principiante/Intermedio/Avanzado), it is not shown to Vectron's end users, and it does not touch the real dataset, the real embeddings, or the real meaning-cube at all. It is an **internal R&D sandbox** — a place to experiment with a single hero particle (and later, thousands of copies of it) in complete isolation from the production scene, so that visual/animation/performance ideas can be pushed to their limits and iterated on quickly, without any risk to the live app.

The code itself documents this intent directly (`particulaConfig.ts`): the playground is, in the user's own words, *"a kind of configurator for the cube"* — whatever combination of visual styles ends up winning gets exported as a JSON config (there's a literal "export configuration" button that copies the full parameter set to the clipboard) and is then manually ported into the real cube's particle system. Every parameter that affects how a particle looks or behaves — birth style, division style, union style, death style, material properties, movement, color rules, even values that aren't yet exposed as UI controls — is centralized in that one config file specifically so a "winning" combination can be handed off completely, without anyone needing to go spelunking through the animation source code to figure out what values were used during testing.

**The goal: a hyper-realistic, energetic, watery/organic particle.** The explicit brief (direct from the user) was: *"don't reuse the existing flat particle, make it hyper-realistic, almost ray-traced."* Literal ray tracing is not viable in a browser at 60fps today, so the approach taken is the closest practical approximation: real physically-based rendering (PBR) via Three.js's `MeshPhysicalMaterial`, tuned specifically to read as **wet / glass-like / alive** rather than a flat plastic ball:

- **Transmission + thickness + IOR** (`transmission: 0.32`, `thickness: 1.6`, `ior: 1.48`) — real light transmission and refraction through the sphere, as if light is genuinely passing through a translucent, glass-or-water-like volume, not just a semi-transparent trick.
- **Iridescence** (`iridescence: 0.5`, `iridescenceIOR: 1.3`) — the subtle oil-on-water color-shifting sheen, contributing to the "watery" read.
- **Clearcoat** (`clearcoat: 0.5`, `clearcoatRoughness: 0.15`) — an extra wet-looking specular layer on top of the base surface, like a droplet's surface tension.
- **Real environment reflections** — a `PMREMGenerator`-baked environment map (from a `RoomEnvironment`, soft colored walls/lights) is generated once and shared across every particle, giving credible reflections/highlights without loading an external HDRI per particle.
- **Real scene lighting** — an ambient light plus a soft directional key light, tuned specifically so the now-much-more-opaque sphere still reads as "glowing with its own light" rather than washed out/overexposed once transmission was tuned down (a real visual bug encountered and fixed during development).

**Motion and "energy," not just a static hyperrealistic sphere.** Each particle has its own per-particle Brownian-drift parameters (amplitude, frequency, phase) so a cluster of them never looks perfectly synchronized/robotic — it reads as organic, living motion. On top of that sits a whole library of **animation variants** for the particle life-cycle: birth (fade-in, energy burst, condensation, germination, quantum flicker, expanding ring, ascent), division/mitosis, union/fusion, and death (currently: bubble-pop), each swappable independently and each tunable in duration/intensity via the same central config. Division specifically got a dedicated **raymarched metaball blob** effect (`metaballBlob.ts`) so that when one particle splits into two, the surface actually deforms and pinches like a real cell dividing, matching the real hero particle's own material rather than a generic placeholder effect. At larger batch sizes (hundreds to low thousands of particles), a subtle "brain-shape" attractor gently reshapes the whole cloud toward an organic, asymmetric silhouette (fuller on top, a sagittal groove down the middle) instead of a plain sphere, purely as a visual richness experiment.

**The problem: what happens to memory/performance when you make a lot of these.** Every one of those hyper-realistic touches — real transmission/refraction, iridescence, clearcoat, environment reflections, real scene lighting — is genuinely expensive to compute, and in the original design *each particle was its own, completely independent 3D object*: its own `SphereGeometry(64, 64)` (a real, dense, 64×64-subdivided sphere mesh — roughly 8,000+ triangles, so it reads as perfectly round and smooth up close) plus its **own separate `MeshPhysicalMaterial` instance**. That means every single particle carries: its own geometry buffer sitting in GPU memory, its own material/shader uniform block, its own full PBR lighting/transmission/reflection computation every frame, and its own individual GPU draw call. None of that is shared. At around **2,000 individual particles**, this was measured live to bring the browser tab to the edge of hanging — the GPU's per-object overhead (draw call submission, shader complexity, transparency/order-dependent blending) and the sheer number of high-poly meshes simultaneously demanding full PBR lighting simply outpaces what a browser tab can push at interactive frame rates. This became a real, concrete ceiling on how large a batch the "mass divide/unite" panel could let someone request, directly limiting how far the lab could be used to explore what happens at true scale (the user's own explicit ask: *"I want to see what happens if we have 25,000"*).

**What was done to fix it.** The core idea is: don't pay full individual-mesh cost for particles nobody is looking at up close. Above a size threshold, particles switch from "hero" quality to a much cheaper shared representation:

1. **GPU instancing above the threshold.** Instead of thousands of separate meshes, particles past the threshold all share **one single geometry** (a much simpler, low-poly `IcosahedronGeometry`) and **one single, much cheaper material** (`MeshBasicNodeMaterial` with just a fresnel/rim-light shader term for a glow, not full PBR), rendered through **one single `THREE.InstancedMesh`** — collapsing what would have been thousands of individual GPU draw calls into one draw call for the entire bulk population. Per-particle position updates bypass Three.js's normal (and comparatively expensive) `Object3D.updateMatrix()` path entirely and write directly into the instance's raw transform buffer — measured live, this cut per-frame cost from roughly 187ms at 25,000 particles down to something that actually fits inside a 16ms frame budget at 60fps.
2. **The threshold itself is tuned, not arbitrary.** It currently sits at 2,000 particles specifically so that "normal-sized" batches (up to a couple thousand) still get the full hyper-realistic hero material *and* the mitosis/fusion animation people actually asked to see, and only genuinely extreme batches (thousands, up to the current cap of 25,000) drop to the cheaper shared tier.
3. **A series of real correctness bugs around that scaling system were found and fixed in this session**, each one independently capable of making a large batch look broken or perform badly even with instancing in place:
   - A flicker at scale caused by a transparency/blending mismatch on the shared instanced material (copied from a similar file without also copying the blending mode that made that combination correct there).
   - A stale-`localStorage` bug where a returning session would keep loading an old, lower cap for the batch size forever, silently preventing anyone from actually reaching the new, higher ceiling.
   - A boundary bug where a batch aimed at *exactly* the instancing threshold never actually triggered the cheap tier at all (an off-by-one in when the check ran relative to when the population count actually changed), so a batch of exactly 2,000 could end up as 1,998 full individual meshes plus only 2 instanced ones — precisely the expensive scenario instancing exists to avoid.
   - A deeper version of the same problem: since batches grow gradually (one split at a time, from a single starting particle), almost every particle in a large batch was created *before* the population count ever crossed the threshold, so it stayed in the expensive individual tier forever, with only the last particle or two ever switching over. Fixed by detecting, at the start of a batch, that its target size will exceed the threshold, and immediately converting the whole existing population plus every new particle created during that batch to the cheap tier from the very first step — instead of waiting for the count to "naturally" cross a line that gradual, one-at-a-time growth would barely ever cross in practice.
   - A subtler shape bug (not a performance bug): the "brain-shape" attractor described above was found, live, to make the entire particle cloud drift further and further away from where it started, unboundedly, the longer a large batch ran — because its silhouette is deliberately *not* symmetric (fuller top, flatter bottom, to actually look brain-like), and the code was recalculating its pull target from the population's *own, currently-drifting* center every frame, which fed the asymmetry back into itself with nothing to anchor it. Fixed by anchoring that pull to the fixed point where every particle actually starts (world origin), removing the runaway feedback entirely.
   - A pacing bug where, once particles could be created "instantly" (no per-mesh animation) at scale, a mass-batch operation with certain speed settings could **double the entire population every single rendered frame** — because completing an operation instantly also freed up its concurrency slot instantly, with nothing left to throttle how many new waves could launch per frame. This made a request for 2,000 particles finish in roughly a tenth of a second, far faster than the camera-follow logic or the spacing/shape logic could possibly react, which is what produced a literal black/blown-out screen (the camera effectively ended up *inside* an instantly-materialized, still-overlapping ball of particles). Fixed by making even the "instant" creation path still hold its concurrency slot for the configured operation duration, exactly like the animated path always did — so growth is fast, but always paced.

**Net effect today:** a batch can scale from 1 particle up to **25,000**, with the small hero population still getting the full hyper-realistic, watery, ray-traced-adjacent material and organic animation the original brief asked for, and the bulk population beyond 2,000 rendering through one shared, GPU-instanced draw call instead of thousands of independent expensive objects — keeping both memory and per-frame GPU/CPU cost bounded regardless of how large a batch someone asks the lab to try.

**Why this matters for Vectron as a whole:** none of this is meant to ship to end users as-is. `/particula` exists purely so that whichever combination of these effects looks and feels best — the exact material tuning, the exact animation timings, the exact large-scale rendering strategy — can be locked in, exported as a config, and *then* deliberately ported into the real meaning-cube that Principiante/Intermedio/Avanzado actually show to the public. It is, quite literally, the R&D lab for "how do we make the real cube look incredible" — decoupled from the real dataset and the real product so that experimentation there can be fast, disposable, and free of any risk to the live app.

## Español

### §1. Qué estamos tratando de lograr con Vectron

Vectron es un **visualizador 3D público, gratuito y de código abierto** que vuelve visible algo que normalmente es completamente invisible: cómo un modelo de lenguaje grande convierte de verdad una palabra, una frase o un documento en *números*, y cómo esos números se pueden comparar, buscar y recuperar. La apuesta detrás de todo el proyecto es que la mayoría de las personas que usan ChatGPT/Claude/Gemini todos los días no tienen ninguna intuición de qué es un "embedding," qué significa "similitud coseno," o qué pasa realmente cuando un chatbot hace RAG (generación aumentada por recuperación) sobre un documento que subiste. El trabajo de Vectron es hacer ese mecanismo *visible* — un espacio 3D real por el que puedes volar, donde palabras que significan cosas parecidas de verdad terminan físicamente cerca unas de otras, porque se colocan usando **embeddings reales** (no un layout de juguete o ilustrativo).

En concreto: cada concepto del dataset pasa por un modelo de embeddings real, produciendo un vector genuino de alta dimensión (768 dimensiones hoy). Ese vector se comprime matemáticamente a 3 coordenadas (hoy mediante una proyección PCA — Análisis de Componentes Principales — hecha a mano; UMAP es una posible mejora futura) para poder colocarse como una partícula luminosa en una escena de Three.js. La distancia y el agrupamiento en ese cubo 3D no son decorativos, pero **tampoco son fieles**: son el mejor resumen LINEAL en 3D de un espacio de 1024 dimensiones. Preserva bien la estructura a gran escala e imperfectamente los vecindarios locales. Las cifras, medidas sobre los embeddings reales de la siembra (`worker/scripts/out/diagnostics.json`): **CP1–3 retienen el 10.89 %** de la varianza, y la preservación de vecindarios da **trustworthiness 0.766 / continuity 0.837 a k=10** — es decir, alrededor de un 23 % de lo que se ve cerca en pantalla NO está cerca en las 1024 dimensiones. Además las coordenadas almacenadas pasan por tres transformaciones (reescalado por percentil por eje, recorte al borde del cubo y una relajación de separación local), así que la distancia en pantalla tampoco es proporcional a la distancia PCA en las zonas densas. **Las listas de vecinos que ves al fijar una partícula se calculan en las 1024 dimensiones completas, no a partir de lo que ves en pantalla.** Cuando escribes una palabra y sus vecinas se iluminan, eso es una consulta real de vecinos más cercanos contra un índice vectorial real (Cloudflare Vectorize), no una tabla de búsqueda inventada.

La ambición de largo plazo, dicha con honestidad en el plan maestro, es grande: un dataset público de **15,000 conceptos bilingües** (hoy pausado alrededor de ~2,263 mientras aterrizan otras features prioritarias de la etapa NOW), un pipeline RAG completo (subes un documento → se parte en fragmentos → los fragmentos se convierten en embeddings → una pregunta recupera los fragmentos más relevantes → un LLM genera una respuesta basada en ellos, todo visualizado), y eventualmente una vista en vivo del propio mecanismo de atención del Transformer. Eso es una construcción de varios meses para un solo desarrollador, así que el proyecto está deliberadamente secuenciado como **DONE → NOW → LATER** en vez de intentarse todo junto — ver `02-master-plan.md` §11 para la tabla exacta de fases (P0…P10).

Todo se libera bajo licencia MIT, alojado en `vectron.kilowatto.com`, con el objetivo explícito de costar efectivamente **$0** en operación estable: el dataset por defecto se precalcula una sola vez al momento de la siembra (no se re-embebe por cada visitante), el camino RAG por defecto corre completamente del lado del cliente vía WebLLM (un LLM local dentro del navegador, sin costo de inferencia en servidor), y cualquier modo RAG "premium" con Claude es opcional, apagado por defecto, y con cuota diaria dura por usuario.

### §2. El contenido didáctico — tres apps separadas, no una app con un interruptor de configuración

Esta es una de las decisiones de producto más importantes y deliberadamente cerradas de todo el proyecto, así que vale la pena explicar *por qué* está estructurado así y no solo *qué* es.

**La idea central:** un adolescente curioso, un estudiante universitario aprendiendo NLP, y alguien con nivel PhD en ML no quieren simplemente "más detalle" en la misma pantalla — quieren una experiencia genuinamente distinta: vocabulario distinto, densidad de información distinta, cosas distintas tratadas como "dadas por sentado" vs. "explicadas," incluso un layout visual distinto. Entonces, en vez de una sola app con un control deslizante que revela/oculta jerga, Vectron entrega **tres apps distintas** que comparten el mismo motor y dataset por debajo pero se presentan de forma completamente diferente. Es una regla cerrada (`OBLIGATORIO`): los nombres son siempre **Principiante / Intermedio / Avanzado** — nunca traducidos a "app para principiantes" / "app universitaria" / "app de investigación" en la interfaz; esas son solo etiquetas internas de audiencia para quienes construyen el producto.

**Principiante ("mapa de asombro")** — audiencia: adolescentes, niños curiosos, personas mayores que se impresionaron con ChatGPT y quieren entender *algo* de cómo funciona. El éxito se ve como que la persona pueda decir, con sus propias palabras, "busca *ideas* cercanas, no las mismas letras" en unos 90 segundos desde que llega. Toda la jerga está prohibida por defecto — nada de "coseno," "ℝⁿ," "BPE," "PCA." Las partículas se leen simplemente como un cielo de ideas relacionadas que se iluminan juntas.

**Intermedio ("laboratorio del mecanismo")** — audiencia: estudiantes universitarios, apuntado específicamente a un currículo de licenciatura en IA. No es una sola pantalla sino un laboratorio con **tres superficies hermanas**: `Cubo` (el mecanismo token → embedding → vecino por coseno, la misma visualización central que Principiante pero ahora correctamente nombrada y explicada), `Transformer` (Entrada → **Contexto** → Atención → Bloques → Predicción, mostrado como un ciclo que se puede recorrer paso a paso), y `RAG` (un archivo externo de documentos → fragmentación → recuperación → alimentando el Contexto → el Transformer). Existe un capítulo específico y cuidadosamente acotado, la **Cámara de Contexto** 3D, dentro de la superficie Transformer — visualiza la *memoria de trabajo del modelo para esta conversación en particular*, y explícitamente nunca se presenta como el mismo espacio de datos que el cubo de significado, para que el estudiante no confunda "el espacio de todos los conceptos" con "lo que el modelo recuerda ahora mismo." Se usa vocabulario correcto de nivel universitario, con tooltips de una sola vez en vez de simplificar de más o asumir conocimiento previo. Lo que Intermedio explícitamente NO muestra: mapas de calor de atención de nivel PhD ni la ecuación literal de softmax/√dₖ en KaTeX — eso pertenece solo al Math Arena de Avanzado.

**Avanzado ("instrumento")** — audiencia: estudiantes de doctorado y científicos de datos / ingenieros de ML en activo que quieren lo real, incluyendo dónde la visualización es una aproximación y dónde no lo es. Aquí la jerga es *obligatoria*, no opcional, pero cada aproximación se declara explícitamente en vez de esconderse. Esta superficie expone: dos tokenizadores en vivo corriendo lado a lado para comparar (el tokenizador WordPiece de BGE vs. el cl100k de GPT), llamadas de embedding en vivo bajo demanda contra Cloudflare Workers AI (limitadas por IP para que el costo se mantenga acotado), una base PCA persistida para que la proyección 3D sea reproducible y estable entre sesiones (no se re-aleatoriza al cargar), consultas por vector individual contra Vectorize, y pasar el mouse sobre cualquier línea de conexión para ver el número real de similitud coseno. El "Math Arena" planeado (permanente, no un panel colapsable de "ocultar toda la matemática") añadirá instrumentos en vivo de Atención/Softmax/Coseno/PCA/Muestreo — tensores a escala de juguete son aceptables ahí siempre que estén claramente etiquetados como ilustrativos, pero las vistas de coseno y PCA deben usar primero los vectores reales del dataset.

**Una capa pedagógica secundaria y cerrada** vive debajo de las tres apps: qué *partes de la oración* son visibles actúa como escalera de dificultad. Principiante muestra solo sustantivos y palabras función (artículos, preposiciones, conjunciones, auxiliares). Intermedio añade adjetivos. Avanzado añade verbos. Esto deliberadamente NO se usó como el eje curricular principal (eso sería un truco superficial de "mostrar/ocultar gramática") — está cerrado únicamente como regla secundaria de visibilidad.

**Dataset actual:** aproximadamente 2,263 conceptos bilingües (español/inglés) curados a mano, repartidos en ~20+ dominios semánticos, cada uno con un embedding real guardado en Vectorize, una taxonomía, rasgos descriptivos, una etiqueta de parte de la oración, y una coordenada 3D. La meta es 15,000 conceptos; el crecimiento está pausado hoy (no por falta de ambición, sino porque el equipo decidió aterrizar primero las features prioritarias de la etapa NOW — composer de frases, animación de morph entre modos, leyendas del HUD, el loader de arranque, RAG lite — antes de seguir gastando presupuesto de curación en tamaño bruto del dataset). El crecimiento de conceptos ahora está en gran parte automatizado vía un Cron job de Cloudflare, en vez de generarse/revisarse manualmente lote por lote.

Cada canal visual en la escena tiene significado, no es decorativo: la posición XYZ viene de la proyección PCA real del embedding; el tono (hue) codifica el dominio semántico raíz del concepto (~20+ colores categóricos); saturación/luminosidad codifica una subcategoría o un atributo continuo dentro de ese dominio; un efecto de halo/pulso muestra relevancia dinámica respecto a lo que la persona acaba de escribir. Cada tarjeta también expone sus atributos como texto plano, así que la codificación nunca depende solo del color (requisito de accesibilidad).

### §4. El laboratorio `/particula` — qué es, y qué estamos tratando de comprobar ahí

**`/particula` no es parte del producto.** No es una de las tres apps públicas (Principiante/Intermedio/Avanzado), no se muestra a quienes usan Vectron, y no toca el dataset real, los embeddings reales, ni el cubo de significado real en absoluto. Es un **sandbox interno de investigación y desarrollo** — un lugar para experimentar con una sola partícula "hero" (y después, miles de copias de ella) en aislamiento completo de la escena de producción, para que las ideas visuales/de animación/de rendimiento se puedan llevar al límite e iterar rápido, sin ningún riesgo para la app en vivo.

El propio código documenta esta intención directamente (`particulaConfig.ts`): el playground es, en palabras del propio usuario, *"una especie de configurador para el cubo"* — la combinación de estilos visuales que termine ganando se exporta como una configuración JSON (hay un botón literal de "exportar configuración" que copia todo el conjunto de parámetros al portapapeles) y después se porta manualmente al sistema de partículas del cubo real. Cada parámetro que afecta cómo se ve o se comporta una partícula — estilo de nacimiento, estilo de división, estilo de unión, estilo de muerte, propiedades del material, movimiento, reglas de color, incluso valores que todavía no están expuestos como controles de UI — está centralizado en ese único archivo de configuración específicamente para que una combinación "ganadora" se pueda entregar completa, sin que nadie tenga que ir a rebuscar en el código fuente de cada animación para descubrir qué valores se usaron durante las pruebas.

**El objetivo: una partícula hiperrealista, con energía, acuosa/orgánica.** El encargo explícito (directo del usuario) fue: *"no reuses la partícula plana existente, que sea hiperrealista, casi ray tracing."* El ray tracing literal no es viable en un navegador a 60fps hoy en día, así que el enfoque tomado es la aproximación práctica más cercana: renderizado físicamente correcto (PBR) real vía `MeshPhysicalMaterial` de Three.js, afinado específicamente para leerse como **mojada / tipo vidrio / viva**, en vez de una bola de plástico plana:

- **Transmisión + espesor + índice de refracción** (`transmission: 0.32`, `thickness: 1.6`, `ior: 1.48`) — transmisión y refracción de luz real a través de la esfera, como si la luz de verdad estuviera atravesando un volumen translúcido tipo vidrio o agua, no solo un truco semi-transparente.
- **Iridiscencia** (`iridescence: 0.5`, `iridescenceIOR: 1.3`) — el sutil brillo cambiante de color tipo mancha de aceite sobre agua, que aporta a la lectura "acuosa."
- **Clearcoat / capa transparente** (`clearcoat: 0.5`, `clearcoatRoughness: 0.15`) — una capa especular extra de aspecto mojado sobre la superficie base, como la tensión superficial de una gota.
- **Reflejos de entorno reales** — un mapa de entorno horneado con `PMREMGenerator` (a partir de un `RoomEnvironment`, paredes/luces suaves de colores) se genera una sola vez y se comparte entre todas las partículas, dando reflejos/highlights creíbles sin cargar un HDRI externo por partícula.
- **Iluminación real de escena** — una luz ambiental más una luz direccional suave, afinadas específicamente para que la esfera, ahora mucho más opaca, se siga leyendo como "brillando con luz propia" en vez de verse lavada/sobreexpuesta una vez que se bajó la transmisión (un bug visual real encontrado y corregido durante el desarrollo).

**Movimiento y "energía," no solo una esfera hiperrealista estática.** Cada partícula tiene sus propios parámetros de deriva tipo browniano (amplitud, frecuencia, fase) para que un grupo de ellas nunca se vea perfectamente sincronizado/robótico — se lee como movimiento orgánico, vivo. Sobre eso hay toda una biblioteca de **variantes de animación** para el ciclo de vida de la partícula: nacimiento (fundido, estallido de energía, condensación, germinación, parpadeo cuántico, anillo expansivo, ascenso), división/mitosis, unión/fusión, y muerte (hoy: burbuja que estalla), cada una intercambiable de forma independiente y ajustable en duración/intensidad desde la misma configuración central. La división en particular tiene un efecto dedicado de **blob metaball raymarcheado** (`metaballBlob.ts`) para que, cuando una partícula se divide en dos, la superficie de verdad se deforme y se estrangule como una célula real dividiéndose, usando el mismo material de la partícula hero real en vez de un efecto genérico de relleno. A tamaños de lote más grandes (cientos hasta unos pocos miles de partículas), un sutil atractor "tipo cerebro" reacomoda con delicadeza toda la nube hacia una silueta orgánica y asimétrica (más llena arriba, con una hendidura sagital al centro) en vez de una esfera simple, puramente como experimento de riqueza visual.

**El problema: qué le pasa a la memoria/rendimiento cuando generamos muchas.** Cada uno de esos toques hiperrealistas — transmisión/refracción real, iridiscencia, clearcoat, reflejos de entorno, iluminación real de escena — es genuinamente caro de calcular, y en el diseño original *cada partícula era su propio objeto 3D completamente independiente*: su propio `SphereGeometry(64, 64)` (una malla esférica real, densa, subdividida 64×64 — más de 8,000 triángulos, para que se vea perfectamente redonda y lisa de cerca) más su **propia instancia separada de `MeshPhysicalMaterial`**. Eso significa que cada partícula individual carga: su propio buffer de geometría en memoria de GPU, su propio bloque de uniforms de material/shader, su propio cálculo completo de iluminación/transmisión/reflejo PBR cada cuadro, y su propia llamada de dibujo (draw call) individual en la GPU. Nada de eso se comparte. Alrededor de **2,000 partículas individuales**, esto se midió en vivo y llevaba a la pestaña del navegador al borde de colgarse — el costo por objeto de la GPU (envío de draw calls, complejidad del shader, mezcla de transparencia dependiente del orden) y la sheer cantidad de mallas de alto detalle pidiendo simultáneamente iluminación PBR completa simplemente supera lo que una pestaña de navegador puede empujar a velocidades de cuadro interactivas. Esto se convirtió en un tope real y concreto de qué tan grande podía ser un lote que el panel de "dividir/unir en masa" permitiera pedir, limitando directamente qué tanto se podía usar el laboratorio para explorar qué pasa a escala de verdad (el pedido explícito del propio usuario: *"quiero ver qué pasa si tenemos 25,000"*).

**Qué se hizo para mejorarlo.** La idea central es: no pagar el costo completo de malla individual por partículas que nadie está mirando de cerca. Por encima de un umbral de tamaño, las partículas cambian de calidad "hero" a una representación compartida mucho más barata:

1. **Instancing por GPU por encima del umbral.** En vez de miles de mallas separadas, las partículas que pasan el umbral comparten todas **una sola geometría** (mucho más simple, un `IcosahedronGeometry` de bajo detalle) y **un solo material, mucho más barato** (`MeshBasicNodeMaterial` con solo un término de shader tipo fresnel/aro de luz para el brillo, no PBR completo), renderizadas mediante **un solo `THREE.InstancedMesh`** — colapsando lo que hubieran sido miles de draw calls individuales de GPU en un único draw call para toda la población masiva. Las actualizaciones de posición por partícula evitan por completo el camino normal (y comparativamente caro) de `Object3D.updateMatrix()` de Three.js, escribiendo directo en el buffer crudo de transformaciones de la instancia — medido en vivo, esto bajó el costo por cuadro de aproximadamente 187ms con 25,000 partículas a algo que de verdad cabe dentro del presupuesto de 16ms por cuadro a 60fps.
2. **El umbral en sí está afinado, no es arbitrario.** Hoy está en 2,000 partículas específicamente para que los lotes de tamaño "normal" (hasta un par de miles) sigan obteniendo el material hero hiperrealista completo *y* la animación de mitosis/fusión que la gente de verdad pidió ver, y solo los lotes genuinamente extremos (miles, hasta el tope actual de 25,000) bajen al nivel compartido más barato.
3. **En esta sesión se encontraron y corrigieron varios bugs reales de corrección alrededor de ese sistema de escalado**, cada uno capaz de forma independiente de hacer que un lote grande se viera roto o rindiera mal aun con el instancing ya en su lugar:
   - Un parpadeo a escala causado por una combinación incorrecta de transparencia/blending en el material instanciado compartido (copiado de un archivo similar sin copiar también el modo de blending que hacía correcta esa combinación ahí).
   - Un bug de `localStorage` desactualizado donde una sesión que regresaba seguía cargando para siempre un tope viejo y más bajo para el tamaño del lote, impidiendo en silencio que cualquiera llegara de verdad al nuevo tope, más alto.
   - Un bug de límite donde un lote apuntado *exactamente* al umbral de instancing nunca activaba de verdad el nivel barato (un error de "uno de más/uno de menos" en cuándo corría la verificación respecto a cuándo cambiaba de verdad el conteo de población), así que un lote de exactamente 2,000 podía terminar como 1,998 mallas individuales completas más solo 2 instanciadas — precisamente el escenario caro que el instancing existe para evitar.
   - Una versión más profunda del mismo problema: como los lotes crecen gradualmente (una división a la vez, desde una sola partícula inicial), casi cada partícula de un lote grande se creaba *antes* de que el conteo de población cruzara jamás el umbral, así que se quedaba en el nivel individual caro para siempre, con solo la última partícula o dos cambiando alguna vez de nivel. Corregido detectando, al arrancar un lote, que su tamaño objetivo va a superar el umbral, y convirtiendo de inmediato toda la población existente más cada partícula nueva creada durante ese lote al nivel barato desde el primer paso — en vez de esperar a que el conteo "naturalmente" cruce una línea que un crecimiento gradual, de a una, casi nunca cruzaría en la práctica.
   - Un bug más sutil de forma (no de rendimiento): se encontró en vivo que el atractor "tipo cerebro" descrito arriba hacía que toda la nube de partículas se alejara cada vez más de donde empezó, sin límite, mientras más durara corriendo un lote grande — porque su silueta deliberadamente NO es simétrica (más llena arriba, más plana abajo, para verse de verdad como un cerebro), y el código recalculaba su objetivo de jalón desde el centro *propio y actualmente a la deriva* de la población en cada cuadro, lo cual realimentaba la asimetría sobre sí misma sin nada que la anclara. Corregido anclando ese jalón al punto fijo donde toda partícula en realidad nace (el origen del mundo), eliminando por completo la realimentación fuera de control.
   - Un bug de ritmo donde, una vez que las partículas se podían crear "al instante" (sin animación por malla) a escala, una operación de lote masivo con ciertos ajustes de velocidad podía **duplicar toda la población en cada cuadro renderizado** — porque completar una operación al instante también liberaba su cupo de concurrencia al instante, sin nada que frenara cuántas oleadas nuevas podían lanzarse por cuadro. Esto hacía que un pedido de 2,000 partículas terminara en aproximadamente una décima de segundo, mucho más rápido de lo que la lógica de seguimiento de cámara o la lógica de espaciado/forma podían reaccionar, lo cual es lo que producía una pantalla literalmente negra/sobreexpuesta (la cámara terminaba efectivamente *dentro* de una bola de partículas materializada al instante, todavía superpuesta). Corregido haciendo que incluso el camino de creación "instantánea" siga reteniendo su cupo de concurrencia durante la duración de operación configurada, exactamente igual que siempre lo hizo el camino animado — así el crecimiento es rápido, pero siempre con ritmo.

**Efecto neto hoy:** un lote puede escalar de 1 partícula hasta **25,000**, con la población hero pequeña obteniendo todavía el material hiperrealista completo, acuoso, casi ray-traced, y la animación orgánica que pedía el encargo original, y la población masiva por encima de 2,000 renderizando mediante un único draw call compartido con instancing de GPU en vez de miles de objetos independientes y caros — manteniendo tanto la memoria como el costo de GPU/CPU por cuadro acotados sin importar qué tan grande sea el lote que alguien le pida al laboratorio probar.

**Por qué esto importa para Vectron en general:** nada de esto está pensado para enviarse a quienes usan el producto tal cual. `/particula` existe puramente para que la combinación de estos efectos que se vea y se sienta mejor — el ajuste exacto del material, los tiempos exactos de animación, la estrategia exacta de render a gran escala — se pueda dejar fija, exportarse como configuración, y *después* portarse deliberadamente al cubo de significado real que Principiante/Intermedio/Avanzado sí muestran al público. Es, literalmente, el laboratorio de investigación y desarrollo para "cómo hacemos que el cubo real se vea increíble" — desacoplado del dataset real y del producto real para que experimentar ahí pueda ser rápido, desechable, y sin ningún riesgo para la app en vivo.
